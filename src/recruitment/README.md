# トレードの確認・変更案・確定処理の境界（0.55.0）

## 0.55.0：Workerの読取確認

[trade-inspection-types.ts](trade-inspection-types.ts)と[world/trade-inspection.ts](../world/trade-inspection.ts)で、提案条件を現在のWorker正本と照合します。UIからは相手チーム・出す選手・獲得する選手・円だけを渡し、自球団・所属・登録・編成・開始状態は保存内の情報を読みます。プレイ／世界／状態版が一致する要求だけを受け付けます。

所属人数と登録・固定希望、補充が必要な一二軍の打順／守備／先発枠、通常救援、未開始試合の明示指定を表示します。支配下人数への呼替え・成否の評価・給与や資金の補完はしません。個別休養・条件別救援等を含めた全変更の事前確認ではなく、現在指定されている役割の読取です。実際の適用時は下記の全案検査が必要です。

現行世界には契約・資金・交渉承認の記録がないため、報告は常に`blocked`です。`trade-inspection-v1`は成立率のモデルではありません。日付・乱数・採番・状態版・保存に作用せず、画面では下書き／世界／状態版の変更時や遅れた応答を無効にします。

## 0.55.0：新世界用の確定処理の境界

[trade-commit.ts](trade-commit.ts)の`commitAcceptedTrade`は、将来のWorker用adapterを通して既存の全案を審査します。UIは承認IDを参照するだけで、acceptedフラグや適用済み台帳を送れません。adapterが保存内の承認・権限・期限・条件を照合し、審査用の入力を構成します。**実交渉と保存adapterは未接続で、現行Workerはこの確定処理を受け付けません。**

- ローカルプレイ・世界・状態版を照合。同じcommandIdの同一入力は、古い状態版でも保存済みreceiptを返し、世界を過去へ戻しません。内容違いは衝突です。
- commandIdだけでなく承認IDと取引IDの再使用も拒否します。発生元の記録は新世界と同時に永続化する契約で、一時Mapでは代用しません。
- 承認した状態版・日付・シーズンを照合し、登録／編成と会計が通った場合だけ、分離した全候補とreceiptを作ります。承認後の変更は再承認を要求する試作フローです。
- adapterの`commit`は状態版・保存版の両方を比較し、全状態・receiptを一つのトランザクションで保存する必要があります。保存成功後にのみ候補を返し、Workerはその候補だけを正本へ公開します。
- abort時は現行正本を維持。成否不明時は他の更新を止め、再読込／同じ指示の再送で永続receiptを照合する必要があります。保存後の任意整理の失敗を取引失敗として返しません。

`TradeCommitSnapshot<State>`は新世界の保存境界を表す型です。別の世界状態やDBを作るものではなく、`State`の適用・検証・永続化を行う新世界adapterはまだありません。能力・成長・個別設定・過去試合・乱数の保持、承認履歴の更新、名簿の再構成、方針版とキャッシュの無効化、receiptの復元をadapterで実装する必要があります。**現行v21のserializerへ渡すと未対応項目が保存されないため、現行保存へ渡してはなりません。**

版は試作`trade-commit-v1`です。成功率・返答日・初期契約・初期資金・経済係数は追加していません。最終仕様の確定や、IndexedDBの原子的保存を実装済みという意味ではありません。

取引ID・有効時点・移動選手・両球団は一度だけ入力し、会計と編成へ共有します。登録・編成のいずれかで止まれば会計の適用案を返さず、会計審査で止まれば登録・編成の適用案も返しません。`ready`だけが全案を持ち、`blocked`は段階と理由だけを持ちます。入力の配列やレコードを更新しません。

これは**変更案を一括して返す処理**です。DBの原子的保存、二重提出の制御、保存失敗時の保護を実装したという意味ではありません。既存の旧世界・保存を変更したり、新しい可変な正本をUIに置いたりしません。

## 登録・資格

- 獲得後の一軍／二軍と新球団での固定希望を明示します。未指定を勝手に一軍・自動へ補いません。
- 人数調整のため、取引する両球団の既存選手の登録も同じ案で変更できます。取引外の球団の変更は受理しません。
- 旧登録を閉じ、新登録を同じゲーム内日付・イベント順から始めます。登録期間は所属期間に含め、同じ選手の期間重複を許しません。
- 外国人資格と投打の役割は入力の明示データを使います。国籍・氏名・主守備位置から推測しません。未記録なら停止します。
- 所属上限、一軍上限、外国人一軍枠とベンチ枠を別々に検査します。育成／支配下の契約区分はまだ持たず、所属人数を支配下人数と呼び替えません。
- 再登録待ちを移籍や一軍固定で消しません。二軍→二軍は既存日を維持し、一軍→二軍の同時変更は現行の試作登録処理と同じ`reentryDays`を使います。移籍の特例を最終確定した規則ではありません。
- 当日試合開始後は停止します。進行状態はWorkerが全試合・dayPlanから判定して渡す想定で、個別指定が存在するかどうかから推測しません。

## 欠員と個別設定

放出選手が入っていた打順・守備・ローテーションは`null`で欠員を表します。元の打順・枠番号・次先発枠・残った選手の順序は変えず、獲得選手を空席へ自動配置しません。通常救援・条件別救援・個別休養と旧球団の固定希望からは、放出選手を除きます。旧固定希望は監査情報へ残し、新球団には明示した希望を使います。

補充するチームの新しい編成案を`squadReplacements`で渡し、打順・守備の整合、先発／救援の重複、現在の所属・登録区分、必要な投手割当、個別休養・条件別救援を検査します。休養・救援条件の数値検査は既存の検査関数を使います。

一軍・二軍の対象チームとも、編成案に欠員や違反が残れば`blocked`にします。原資料では理想案の未設定は許容され、試合開始時までに完成させる必要があります。**今回の「適用前の変更案では補充済みを要求する」流れは試作`trade-roster-plan-v1`であり、S10の未決定だった欠員解消導線を最終確定したものではありません。** 実際の編集画面への導線は未接続です。

能力・個人練習・成長・体力・登板履歴はこの処理で作り直しません。選手IDを維持し、所属変更だけで未知の値を生成したり疲労を初期化したりしません。チーム全体の方針・版更新と、個人状態を新世界へ接続する処理は次工程です。

## 試合別指定と過去記録

- 完了・開始済み試合と過去の日付の指定は保持します。実試合のfixture・記録・当時の氏名／球団・確定ベンチ・成績は入力対象にせず、変更しません。
- 対象球団の未開始試合で登録対象外になる選手を含む打順・先発・ベンチ指定は、その指定単位で解除し、試合IDと解除した項目を監査情報へ残します。
- 残った個別指定も検査します。ベンチ指定がなくても、先発打順と先発投手だけで人数や外国人ベンチ枠を超える案は止めます。
- 無関係な球団・有効な指定を巻き込まず、標準編成への復帰先にも補充済みの案を要求します。未開始指定の解除方法はこの試作の実装判断です。
